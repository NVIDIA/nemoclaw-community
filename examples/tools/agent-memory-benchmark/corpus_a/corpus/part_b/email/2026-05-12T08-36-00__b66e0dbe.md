> we treat it like a code file. We should mark the static prefix portion explicitly

Strong yes on the marker block. Let me sketch what I'm thinking and you tell me if I'm overdesigning:

```
<!-- prefix-stable:start -->
... system prompt content the provider caches ...
<!-- prefix-stable:end -->

<!-- per-call -->
... user-specific portion ...
```

The CI test I'm writing renders both blocks, computes a stable hash of `prefix-stable`, and stores it in `tests/atlas/prompts/prefix_hashes.txt`. On every render in CI, recompute and diff against the stored hash. If it changes, test fails loudly with a message like "the stable prefix changed — was that intentional? If so, regenerate the hash file with `make refresh-prompt-hashes`."

That gets us:
- No silent invalidation (the situation we just had).
- Explicit acknowledgement on every legit prefix change (paper trail).
- Hash file in git, so we can see prefix-change history.

Cost: one extra test, ~200 LoC. Worth it.

The alternative — runtime check that the cache hit ratio stays high — works too but is reactive. I'd rather catch it pre-merge.

Doing the simpler version first (byte-equality across two contexts) since you wanted it fast. Hash-file version as a follow-up.
