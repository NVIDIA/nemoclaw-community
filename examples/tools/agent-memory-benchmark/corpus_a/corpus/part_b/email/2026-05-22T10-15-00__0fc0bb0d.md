### ReviewBot Summary

The change introduces a per-session wiki read cache and threads it through `ingest/session.py` and the consolidate path. The shape is reasonable but the cache currently shares mutable list values with callers, the invalidation hook fires before the mutex is actually released, and a couple of code paths can populate the cache with partial reads when an upstream call fails. None of these are catastrophic, but two of them will cause stale data on retry which is exactly the failure mode this design tries to avoid.

**Confidence Score: 3/5**

**P1 — `WikiCache.get` returns shared list references; callers can mutate cached payloads**

`WikiCache.get` returns the same `list[PageRef]` object that's stored in `self._entries`. The consolidate path appends synthesized "summary" entries to the returned list before re-passing it to the prompt builder, which means the next caller in the same session sees the mutated list. This was the entire class of bug the per-session cache was supposed to remove. Return a shallow copy, or freeze the value to a tuple at insert time.

```python
def get(self, page_id: str) -> tuple[PageRef, ...] | None:
    entry = self._entries.get(page_id)
    if entry is None:
        return None
    return entry.pages  # already a tuple, immutable
```

Change the internal storage to a `tuple[PageRef, ...]` (set at insert time in `WikiCache.put`) and update the return type of `get` accordingly. Update `src/atlas/services/rollup_service.py` so it does not mutate the returned sequence in place — copy into a local list if it needs to append synthesized entries. Add a unit test in `tests/ingest/test_wiki_cache.py` that gets a value, mutates the returned object, then re-gets the same key and asserts the second read is unchanged.

**P1 — Cache invalidation hook fires before the wiki group mutex is released**

In `src/atlas/ingest/session.py::WaveSession.commit`, the order is: `cache.invalidate_all()` → `wiki_mutex.release()`. A concurrent reader that's blocked on the mutex will unblock the instant the release happens and may observe the cache being repopulated by a *different* session that grabbed the lock first. Move the invalidate call to happen after the mutex is released, or have invalidate take the mutex itself (preferred — that's the contract documented in `docs/design/wave_ingest.md`).

```python
# after
self._wiki_mutex.release()
self._cache.invalidate_all()  # invalidate after lock release
```

<details><summary>Prompt To Fix With AI</summary>

> In `src/atlas/ingest/session.py`, the `WaveSession.commit` method calls `self._cache.invalidate_all()` before `self._wiki_mutex.release()`. Swap the order so invalidation happens after release. Then add an assertion at the top of `WikiCache.invalidate_all` that the wiki group mutex is *not* currently held by the calling session (use `mutex.holder() is not self.session_id`). Add a regression test that simulates two sessions hitting commit at the same time and verifies neither observes a half-invalidated cache.

</details>

**P2 — Failed wiki read can leave a partial entry in the cache**

`WikiCache.put_from_loader` accepts whatever the loader returns, including the case where the loader caught a `WikiNotFound` and returned an empty list. That empty list is then cached as if it were a successful empty page, so subsequent reads in the same session will return "page exists but is empty" instead of triggering a fresh fetch. Either differentiate "miss" from "empty" in the cache value, or skip caching when the loader signals an error via a sentinel.

```yaml
# proposed entry shape
entries:
  page_id:
    pages: tuple[PageRef, ...]
    status: ok | empty | failed   # only cache when status == ok
```

<details><summary>Prompt To Fix With AI</summary>

> In `src/atlas/ingest/wiki_cache.py`, change `WikiCache.put_from_loader` to take a `CacheLoadResult` that carries both the pages and a status enum (`ok`, `empty`, `failed`). Only store entries with `status == ok` or `status == empty` — never `failed`. Update callers in `src/atlas/stores/wiki_store.py` to construct the result properly. Add tests that simulate a transient loader failure followed by a successful retry within the same session and assert the retry actually re-fetches.

</details>
