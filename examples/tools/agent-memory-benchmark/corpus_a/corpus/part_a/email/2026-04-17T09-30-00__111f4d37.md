#### P2 — Stage phase runs sources sequentially

`Orchestrator.dispatch` awaits each `wave.stage(...)` in a `for` loop. Since stage is pure-read (no writes), it can be parallelised with `asyncio.gather`. On a typical wave with email + chat + wiki this is the difference between ~450ms and ~180ms, which matters more once the prefix-cache work lands.

```python
# src/atlas/ingest/orchestrator.py
staged = await asyncio.gather(
    *(self._waves[s].stage(self._conn) for s in sources)
)
```

#### P1 — Migration adds `error_type` but does not backfill historical failed rows

The migration `0042_add_error_type.sql` adds the column with `DEFAULT NULL`. Existing rows in `email_items`, `chat_items`, and `wiki_items` with `state='failed'` will have `error_type IS NULL`, which makes the consolidate job's `GROUP BY error_type` route those into a single "unknown" bucket. Either backfill `error_type='LegacyError'` for pre-migration rows or have the consolidate job treat NULL as a per-row group.

```sql
-- src/atlas/db/migrations/0042_add_error_type.sql
ALTER TABLE email_items ADD COLUMN error_type TEXT;
UPDATE email_items SET error_type = 'LegacyError'
  WHERE state = 'failed' AND error_type IS NULL;
-- repeat for chat_items, wiki_items
```

Add a migration test under `tests/db/test_migrations.py` asserting no rows end the migration with `state='failed' AND error_type IS NULL`.
