Alex,

I've been looking at how Beacon's agent runtime and Atlas's diverged over the last quarter and I think we should pull a shared abstraction out before the gap gets worse. Want to put a proposal in front of you before I write a spec.

The pain points on the Beacon side:

- Job submission. We rolled our own task-registry pattern that's 80% the same as yours, but the liveness-resolution semantics drift in one place (we treat `status=running` as authoritative; you derive from the registry). Anya hit a bug last week that would have been a non-issue on your code path.
- Prompt prefix cache reuse. We pay the cache-miss penalty on every Beacon eval run because we're not threading the prefix the same way you do.
- Background job scheduling — we copy-pasted your cron entrypoint pattern and it's started to bit-rot.

Proposal: extract a `atlas.agent.runtime` core that both products consume. Atlas keeps its current behavior bit-for-bit; Beacon migrates onto it over Q3.

Worth a 30-min sync next week? I'll prep one slide.

— Rohan
