#### P1 — Single orchestrator transaction blocks concurrent readers for the full wave

Now that `Orchestrator.dispatch` opens one `BEGIN IMMEDIATE` for the whole wave, any other coroutine reading from the same `atlas.db` connection (the triage path, the API status route) will block until the wave commits. Under realistic load that's 200–600ms per wave, which is enough to make the WebSocket heartbeat stutter. Either use a separate writer connection or move to a per-wave write-ahead-log staging table that flushes in one short transaction at the end.

```python
# src/atlas/ingest/orchestrator.py
async def dispatch(self, sources: list[Source]) -> WaveResult:
    # Stage to in-memory buffers; one short BEGIN at the end.
    staged = [await self._waves[s].stage(self._conn) for s in sources]
    with self._writer_conn:
        return WaveResult.merge(self._commit_all(staged))
```

#### P1 — `_mark_failed` loses the exception type

`WaveBase._mark_failed` stores `str(err)` in `wave_results.error_text` but drops `type(err).__name__`. Downstream the consolidate job groups failures by error type to surface "wiki write timeout" vs "wiki write conflict". With only the message text, transient errors with variable suffixes (e.g. `database is locked (after 3.2s)`) won't group.

```python
# src/atlas/ingest/wave_base.py
def _mark_failed(self, conn, ids, err: BaseException) -> None:
    conn.execute(
        f"UPDATE {self.table} SET state='failed', "
        f"error_type=?, error_text=? WHERE id IN (?)",
        (type(err).__name__, str(err), ids),
    )
```
