Rohan,

Quick reactions to Anya's list.

> 1. Submit + wait is awkward

Easy. Entrypoint already returns a handle; we just don't document the non-blocking path. Will fix.

> 2. Cancel queued jobs

Doable as a registry state transition. Will spec.

> 3. JSON-in-TEXT metadata is opaque

Disagree on the framing. It's intentional — keeps the registry stable across per-job payload changes. If you want queryable metadata, do per-kind tables, don't flatten the registry. Discuss Wed.

> 4. Retry semantics

The hard one. Atlas needs at-most-once for jobs that mutate `wiki/` — re-running a half-done wiki update corrupts the page. Beacon wants at-least-once for eval. Shared core has to expose retry as per-job-kind, not global. Implementation moderate; design cost is "people must declare it."

> 5. Concurrency caps

Same axis as (4). One declaration site, two settings.

Pre-meeting ask: Anya brings an actual Beacon eval job as the retry test case.

One flag — wiki group mutex. (对，就是 mutex 那个老问题.) Wave-ingest depends on it serializing wiki writes. Scope it OUT of the shared core for v1 — Atlas keeps it, Beacon doesn't touch wiki state — revisit if Beacon's roadmap shifts.

See you Wed.

— Alex
