Invite landed, thanks.

One more thing I noticed re-reading the doc on the train:

> The 2 that tripped the mutex get re-queued at the head — same wave, next tick.

Doesn't that starve the next wave from making progress if the mutex contention is persistent? Like if the wiki writer is slow for some reason (Compass is pumping in metrics, whatever), wave N keeps re-queuing its tail, wave N+1 never gets dispatched. Worst case the whole pipeline stalls behind a single slow wiki group.

I'd argue we should cap the re-queue count per item — say 3 — and then it drops to backfill, not waits twice. Otherwise the "recent path stays fast" promise in the design intro isn't really true under load.

Not blocking the MR, but worth a paragraph in `## Notes`.

— Jordan
