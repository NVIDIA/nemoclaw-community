All good questions. Quick takes, more in person if needed:

> 1. Trim boundary — Why not per-token?

Considered it. The reason for section-level is the provider's prefix cache works on prefix-byte-equality — they don't do longest-common-prefix at the token level cheaply. So per-token trimming would still need to align to a section boundary to actually benefit from the cache. We'd be doing more work for the same effective ceiling. Open to being wrong here; if you have a counter-experiment in mind let's run it.

> 2. Versioning ... two workers disagreeing about what to trim?

Good catch. Plan was to embed an `algo_version: 1` field in the trimmed prefix as a comment, and refuse to use a cached entry if the version doesn't match worker. Belt-and-suspenders. I'll spell that out in the spec.

> 3. Backfill ... does the trim see them as stable across runs?

Stable. The trim function is pure over (prefix_input, algo_version). Same inputs → same output. Backfill re-renders are byte-identical to the original, so cache hits.
