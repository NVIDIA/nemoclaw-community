> (a) Where does the worker discover its own algo_version?

Compiled in. The rolling-deploy dip is real but bounded: only the prefixes rendered during the deploy window are affected, and they get re-rendered on next call by whichever worker picks them up. Steady state restores within an hour. I'll add a "rolling deploys cause a 10-min cache hit dip" note to `## Key Considerations`.

> (b) ... if the algo regresses ...

Keep. Same reasoning you had — they're still valid prefixes from the provider's POV. Provider-side LRU handles eviction. Worth noting that during the regression window, the cache hit rate will mechanically be lower because v1 entries no longer match v2 lookups — but that's the same cost as a fresh deploy.

Will push spec revision tonight with both notes. Tagging you for review tomorrow morning.

One forward-looking thing while we're here: should the trim algorithm be made pluggable from day 1, or do we YAGNI it? Beacon may want a slightly different shape (Rohan mentioned their prefix is structurally different — fewer sections, more long-form context). If we hardcode trim logic to Atlas's shape, they're stuck either copying it or asking us to extend.

My lean: pluggable, but only one impl shipped. Defines the seam, costs ~50 LoC.
