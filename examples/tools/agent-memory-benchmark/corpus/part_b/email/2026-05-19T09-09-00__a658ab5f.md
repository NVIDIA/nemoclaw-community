> should the trim algorithm be made pluggable from day 1, or do we YAGNI it?

I'd YAGNI it, but with a caveat: keep the trim function pure and the call site narrow so a future swap is mechanical. The 50 LoC for the seam is cheap, but the *interface contract* of what a "trim impl" looks like is the expensive part — and we don't know enough about Beacon's shape to design that contract right today. If we ship a plugin point now, Rohan will write to it, and then we'll discover the contract was wrong and either break Beacon or version the interface. Worse than just calling them when the time comes.

Concrete suggestion: keep the function pure, slap a `# pluggable: see <issue>` comment on top of `trim_prefix()`, file an issue for "evaluate trim plugin interface when Beacon's needs are clearer." That's enough seam-marking without committing to a design.

(I know we usually disagree on this kind of thing — you tend to like seams earlier, I tend to like them later. Happy to be overruled here, this is a judgment call.)
