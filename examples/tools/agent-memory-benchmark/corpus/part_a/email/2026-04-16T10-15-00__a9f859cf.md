### ReviewBot Summary

This MR splits the ingest pipeline into per-type wave classes (`WaveEmail`, `WaveChat`, `WaveWiki`) and routes through a slimmed `orchestrator.dispatch`. The direction is good, but the new wave classes duplicate state-transition logic that used to live in `Wave._commit`, and the wave-commit path now opens a SQLite transaction per source instead of once per batch. I also see a missing `await` on the wiki-side flush. Confidence is limited by the absence of a multi-wave concurrent test.

**Confidence Score: 3/5**

---

#### P1 — Per-source transactions break the wave-commit atomicity invariant

`WaveEmail._commit`, `WaveChat._commit`, and `WaveWiki._commit` each open their own `conn.execute("BEGIN")`. Previously the orchestrator wrapped the whole wave in one transaction, so a crash mid-wave would roll back partial writes. With per-source transactions, a wiki-wave failure after a successful email-wave commit leaves the watermarks inconsistent across sources. This violates the wave-ingest contract in `docs/sot/designs/wave_ingest.md`.

```python
# src/atlas/ingest/orchestrator.py
def dispatch(self, sources: list[Source]) -> WaveResult:
    with self._conn:  # single transaction across all sub-waves
        results = [self._waves[s].run(self._conn) for s in sources]
    return WaveResult.merge(results)
```

<details>
<summary>Prompt To Fix With AI</summary>

> In `src/atlas/ingest/orchestrator.py`, wrap the entire wave dispatch in a single SQLite transaction managed by the orchestrator. Remove the `BEGIN`/`COMMIT` calls inside `WaveEmail._commit`, `WaveChat._commit`, and `WaveWiki._commit`; have them write through the shared connection. Update `docs/sot/designs/wave_ingest.md` to reflect that the atomicity boundary is the orchestrator, not the per-source wave.

</details>

#### P1 — Missing `await` on `WaveWiki._flush_async`

`WaveWiki.run` calls `self._flush_async()` without `await`, so the coroutine is created and dropped. Under typical load this happens to work because the flush is short, but on the wiki path it causes the watermark in `.ingest_state.json` to advance before the writes have actually landed.

```python
# src/atlas/ingest/wave_wiki.py
async def run(self, conn: sqlite3.Connection) -> WaveResult:
    items = self._fetch_pending(conn)
    await self._flush_async(items)  # was: self._flush_async(items)
    return WaveResult(written=len(items))
```

<details>
<summary>Prompt To Fix With AI</summary>

> In `src/atlas/ingest/wave_wiki.py`, add `await` in front of every call to `self._flush_async(...)`. Add a unit test under `tests/ingest/test_wave_wiki.py` that asserts the watermark is only advanced after the awaited flush returns.

</details>
