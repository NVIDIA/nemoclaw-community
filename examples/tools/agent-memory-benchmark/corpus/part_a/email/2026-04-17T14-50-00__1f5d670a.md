#### P1 — `asyncio.gather` swallows secondary stage errors

`asyncio.gather(*stages)` (without `return_exceptions=True`) cancels the remaining tasks the moment one raises. If email and wiki both fail in the same wave, only the email failure is recorded; the wiki rows are silently left in `state='attempted'` (never `'failed'`), so the next wave will retry them but won't surface the original error to the consolidate job.

```python
# src/atlas/ingest/orchestrator.py
results = await asyncio.gather(
    *(self._waves[s].stage(self._conn) for s in sources),
    return_exceptions=True,
)
for src, result in zip(sources, results, strict=True):
    if isinstance(result, BaseException):
        await self._waves[src].mark_stage_failed(self._conn, result)
```

#### P2 — `WaveWiki.stage` does an unbounded scan

`WaveWiki.stage` reads every row in `wiki_items WHERE state='pending'`. There is no `LIMIT` and no pagination by `wave_seq`. For the backlog scenario (wave_backfill catching up after a long pause) this is a multi-second query that holds the read connection. The email and chat waves are already paginated by `wave_state.last_wave_seq`; the wiki wave should match.

```python
# src/atlas/ingest/wave_wiki.py
def _fetch_pending(self, conn) -> list[WikiItem]:
    return conn.execute(
        "SELECT id, source_id, wave_seq, payload FROM wiki_items "
        "WHERE state='pending' AND wave_seq > ? "
        "ORDER BY wave_seq LIMIT ?",
        (self._cursor, self._batch_size),
    ).fetchall()
```
