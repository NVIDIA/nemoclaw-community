Going through your comments:

> (1) `WaveDispatcher.dispatch_next()` — you're acquiring the global mutex around the wave assembly

You're right and I'm embarrassed. The mutex acquisition was supposed to scope to the commit only; I dragged it up during a refactor and never moved it back. Fixed in a new commit, pushed. Now `dispatch_next()` is purely in-memory and the per-item commit grabs the mutex inside `commit_item()`. The integration test for stalling actually catches this now.

> (2) ... `wiki_write_contention_total` and label by caller.

Renamed, added the `caller` label (values: `wave_ingest`, `consolidate`, `manual`). Will update the alert query in metricswatch in a follow-up MR — don't want to mix monitoring config into this one.

> (3) Test coverage for the cap-at-3

Added. New test in `tests/atlas/ingest/test_wave_backfill.py` — runs a wave with a fake mutex that's permanently held, asserts items land in backfill with `reason=mutex_contention` after 3 attempts. Also added a regression test for the cooldown (back-of-queue) behavior since I broke it once and don't want to break it again.
