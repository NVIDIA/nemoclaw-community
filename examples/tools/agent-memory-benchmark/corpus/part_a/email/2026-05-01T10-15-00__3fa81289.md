#### P1 — Commit-time lock held longer than necessary

`Orchestrator._commit_all` now does `BEGIN IMMEDIATE` and then runs `_commit` for every source sequentially under that lock. Sources don't share state, so each per-source commit could happen under its own short transaction; the cross-source advance of `last_wave_seq` is the only thing that truly needs the immediate lock. Hold the lock for the seq advance only, then commit per-source data in independent short writes.

```python
# src/atlas/ingest/orchestrator.py
def _commit_all(self, staged: list[StagedWave]) -> WaveResult:
    with self._writer_conn:
        next_seq = self._state.advance(self._writer_conn, len(staged))
    # per-source writes — independent short transactions
    return WaveResult.merge(
        wave.commit(self._writer_conn, seq) for wave, seq in zip(staged, next_seq)
    )
```

#### P2 — Regression test uses `time.sleep` for synchronisation

`tests/ingest/test_wave_commit_race.py::test_two_waves_race` schedules two coroutines and sleeps for 50ms to "let them both reach the read". On a loaded CI runner this barrier is unreliable; the race window can close before both coroutines arrive. Use an `asyncio.Barrier(2)` (or an `Event` pair) so the test deterministically synchronises both coroutines at the read point.

```python
# tests/ingest/test_wave_commit_race.py
async def test_two_waves_race():
    barrier = asyncio.Barrier(2)
    async def wave_run(orch):
        await barrier.wait()
        return await orch.dispatch([...])
    results = await asyncio.gather(wave_run(o1), wave_run(o2))
    assert len({r.last_seq for r in results}) == 2  # no duplicate seq
```

<details>
<summary>Prompt To Fix With AI</summary>

> Update `tests/ingest/test_wave_commit_race.py` to replace the `time.sleep(0.05)` barrier with `asyncio.Barrier(2)`. Both wave coroutines should call `barrier.wait()` immediately before the `dispatch` call so they enter the critical section simultaneously.

</details>

#### P1 — `WaveStateStore.advance` swallows `database is locked`

```python
# src/atlas/stores/wave_state_store.py
try:
    cur.execute("UPDATE wave_state SET last_wave_seq = ? ...")
except sqlite3.OperationalError as e:
    logger.info("wave_state advance skipped", err=str(e))
    return None
```

This `except` was added to suppress noisy retries from an earlier version. Now that the commit path uses `BEGIN IMMEDIATE`, a `database is locked` here means the immediate lock could not be acquired within the SQLite busy-timeout — exactly the failure mode the MR aims to expose. Log at `error`, do not return `None`; let the caller decide whether to retry.

<details>
<summary>Prompt To Fix With AI</summary>

> In `src/atlas/stores/wave_state_store.py`, remove the swallow-and-return-None branch on `sqlite3.OperationalError` inside `advance`. Re-raise so the orchestrator can either retry with backoff or mark the wave as `stage_failed`. Add a test in `tests/stores/test_wave_state_store.py` that asserts the exception propagates when the lock can't be acquired.

</details>
